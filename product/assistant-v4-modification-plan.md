# 助手模块 V4 修改方案

日期：2026-09-23

基线：本地 `assistant` 分支，提交 `a464631`。
状态：实现仍在进行；助手数据模型、服务契约、Node/Worker API、本地任务主链路与 V4 页面主体已在本分支落地，类型检查及 H5/Sites 构建通过。尚未完成浏览器逐屏原型验收；模型、语音、附件和外部工具集成也未接入。不包含提交、推送或云端部署。逐屏视觉验收状态见仓库根目录 `design-qa.md`。

## 1. 结论与依据

可以按附件修改，但这是从“准备稿生成工具”升级为“会话 + 可持续执行任务”的改造，不只是替换页面样式。

本次依据：

- `doc/Mixture-X-助手模块-开发原型与规范-V4.zip` 内的 V4 设计规范 DOCX 和五张原型长图。
- `doc/screens/` 中的补充页面截图。
- 当前仓库前端、Node 服务、Worker 入口、数据契约和存储实现。

文档描述交互和规则，长图用于落实布局与视觉；补充截图存在冲突时，以 V4 文档和长图为准。压缩包未包含文档提到的 `prototype.html`，不能据此复用交互源码；`screens/A00-home.png` 是空白图，首页以长图为依据。原型里的示例人物、来源数量、进度、电脑名称、同步结果不能作为真实业务数据。

建议保留现有 TypeScript、原生 DOM、Node 服务及 Worker 适配结构，不引入 React/Vue，不改写整个项目。修改范围以助手为主，保留“今日、记忆、我的”已有功能，仅增加必要的跳转和数据引用。

## 2. 现状与差距

| 方面 | 当前实现 | V4 目标与修改方向 |
| --- | --- | --- |
| 核心流程 | 选择事项、填写要求、生成准备稿、编辑并导出 Word | 提问、判断模式、会话、升级任务、执行、追问或确认、交付 |
| 前端组织 | `web/app.ts` 集中渲染；助手是 overview/prepare/artifact 三阶段 | 拆出助手内部视图和状态管理，按会话和任务恢复页面 |
| 回答能力 | `src/h5-preparation.ts` 主要是模板和规则生成 | 新增模型接入；现有模板不能冒充通用 Chatbot |
| 任务执行 | 准备和导出主要在请求内完成 | 请求快速返回任务标识，后台执行，持久化状态和检查点 |
| 数据 | 事项、记录、上下文、准备稿、导出计划和运行记录 | 新增会话、消息、任务、步骤、追问、证据选择和授权 |
| 证据 | 已有记录版本、事项上下文、来源引用 | 增加可解释的依据面板、排除证据、重算和失效判断 |
| 结果 | 已有结构化准备稿、DOCX 导出和导出恢复逻辑 | 增加任务结果卡、轻量预览、分享、继续修改和交付状态 |
| 外部工具 | 不具备原型展示的完整日历、云盘、桌面执行能力 | 按真实接入能力逐项开放；授权界面不等于已经接通工具 |

已有 `ExportService` 的确认执行、运行占用、文件校验和结果核对能力应复用，不另造一套不兼容的导出流程。

## 3. 哪些是文档要求，哪些是技术设计

| 项目 | 来源与处理 |
| --- | --- |
| Chatbot / Agent 双模式、升级保留上下文 | V4 明确要求 |
| 后台继续、暂停恢复、失败从检查点恢复 | V4 明确要求；需要后端真实支持 |
| 外部写操作确认、禁止自动处理付款与验证码 | V4 明确要求 |
| Session、Task、Step、Evidence、Artifact、Confirmation、ToolGrant | V4 给出的最低数据模型；需要补全消息等工程字段 |
| D1、R2、PostgreSQL、JSON 文件、具体模型厂商 | V4 未指定，不应说成 PRD 要求 |
| 保留原生 TypeScript、独立 AssistantStore、增量轮询 | 本方案的工程建议，可以讨论调整 |
| 本地优先完成、云端执行器后续接入 | 本方案建议的实施顺序，不是删减 V4 验收目标 |

当前本地路径使用 JSON 状态和本地文件；云端代码有 D1 状态、R2 文件适配。仓库中的 PostgreSQL 适配器不是当前 H5 状态存储的直接替换实现，本次不启用它，也不为了助手改造引入数据库迁移到 PostgreSQL 的额外工程。

## 4. 页面与交互修改

| A00F | 稍后提醒的时间选择；忽略后短时撤销；保存处理状态 |
| A01 | 自动、仅问答、执行任务的底部选择面板；立即生效并显示当前模式 |

| C01 / C02 / C03 | 展开输入、录音与转写、录音/文件/图片/记忆入口；使用系统键盘，不绘制假键盘 |
| S01 | 复用空白、加载、离线、权限不足和错误状态组件 |

### 视觉落地

- 使用 V4 的暖白背景 `#FBF8F3`、白色卡片、珊瑚橙 `#FF6A45`、主文字 `#141820` 和辅助文字 `#6F7B8E`；蓝、绿、黄、红表示相应状态。
- 按 4px 网格落实留白、圆角和层级；文档中的 pt 尺寸需转为适合 Web 的视觉尺度，不机械放大所有文字。
- 保留当前应用外壳和底部导航；助手样式使用局部作用域，防止影响其他三个模块。
- 适配手机窄屏、软键盘、底部安全区和桌面容器。输入区不能覆盖最后一条消息。
- 交互热区至少 44px；普通文字对比度目标 4.5:1；状态同时使用文字和图标。
- 进度更新不重建整棵 DOM，避免输入焦点、选区、滚动位置丢失。

## 5. 前端组织方案

建议新增以下模块，名称为拟定结构，不表示文件已经存在：

```text
web/assistant/
  index.ts          助手入口及与其他模块的桥接
  router.ts         内部视图、返回行为、恢复定位
  store.ts          会话缓存、输入草稿、加载与错误状态
  api.ts            助手接口和响应校验
  views/            首页、会话、任务详情、证据、权限
  components/       输入区、计划卡、步骤、结果卡、底部面板
```

`web/app.ts` 只负责应用外壳和模块切换。其他模块通过统一入口传入事项、记录或准备稿标识，不直接操作助手内部状态。

导航保存会话/任务标识，使刷新、浏览器返回、切换标签后能够恢复。已提交消息和任务状态以后端为准；本地仅缓存草稿、选中面板和滚动位置。离线不伪造“已发送”，恢复后通过幂等键提交。

工程配套不能遗漏：

- `web/tsconfig.json` 当前只包含根层 TS 文件，需覆盖新增子目录。
- `scripts/build-h5.ts` 保留模块路径，但 Node 静态路由目前只允许根层 JS，需要安全支持构建后的嵌套资源，保留路径越界检查。
- Worker 构建使用 esbuild；新增样式或资源必须同时覆盖本地构建和 Worker 构建，避免只在一端可用。

## 6. 数据保存方案

### 6.1 业务实体

| 实体 | 主要字段与用途 |
| --- | --- |
| AssistantSession | id、ownerId、mode、title、contextRefs、createdAt、updatedAt |
| AssistantMessage | sessionId、角色、内容、附件引用、发送状态、客户端幂等键 |
| Task | sessionId、goal、status、progress、currentStep、executor、eta、revision、runVersion |
| TaskPlan / TaskStep | 计划版本、步骤顺序、状态、输入输出引用、执行时间、错误和检查点 |
| InputRequest | 待回答问题、选项、推荐项、回答及其对应的任务版本 |
| Evidence | 来源类型、记录标识及版本、摘要、是否纳入、排除原因 |
| Artifact | 关联现有准备稿/导出结果、类型、名称、位置、预览、交付与同步状态 |
| Confirmation | 动作、精确参数、风险、任务/计划版本、确认状态和过期条件 |
| ToolGrant | 所属用户、工具、范围、有效期、状态和确认策略 |
| TaskEvent / ToolExecution | 增量事件、执行幂等键、尝试次数、外部结果及核对状态 |
| SuggestionDisposition | 建议的稍后处理时间、忽略状态和撤销窗口 |

后四类中的部分字段，以及消息、追问、版本和执行记录，是为实现 V4 行为补充的工程设计，不是声称文档逐字指定了这些表。

MVP 采用一个会话最多绑定一个任务，任务可有多个执行版本。纯问答不创建任务；点击处理建议时创建草稿任务，确认计划后才开始执行。完成后继续修改，保留原交付物和回执，新建执行版本，不覆盖历史结果。

### 6.2 存储选择

建议新增独立 `AssistantStore`，通过标识引用现有事项、记录、准备稿和导出记录，不把无限增长的消息塞进原有整个状态 JSON。

- 本地：独立的助手状态目录与附件目录，使用版本化快照、原子落盘和写入协调；备份后再升级数据格式。与旧 H5 状态之间的跨存储操作用执行记录和幂等恢复处理，不能假设两个文件能够自动形成事务。
- 云端：保留 D1/R2 适配方向，但新增按实体保存的助手表、索引和文件命名空间。D1 现有 `mx_state` 是整份 JSON，代码有约 1.5MB 上限，不适合直接累加长会话；R2 当前主要支持导出 Word，不能直接当作任意附件接口。
- 所有云端查询、文件读取和写入均限定认证用户；本地单用户常量不能直接变成云端会话的全局 owner。
- 历史准备稿继续可读、可导出；不伪造旧消息或已完成的任务过程。必要时以“历史准备稿”入口展示。

此方案不要求本地安装 PostgreSQL，也不要求先开通 Cloudflare 才能开发。云端数据库变更和发布需要另行安排。

## 7. 后端和任务执行

建议拆出助手契约、应用服务、共享路由、执行器、模型适配器、工具注册表和证据选择服务，让 Node 与 Worker 共用业务规则。

### 接口范围

以 `/api/assistant/` 为独立接口空间，增加：

- 首页建议与分段列表；会话创建、读取、消息提交与历史分页。
- 模式选择、升级预览与确认升级。
- 任务创建、计划编辑、启动、暂停、继续、取消、失败恢复。
- 追问回答、动作确认、证据读取与排除。
- 工具状态与授权管理；附件上传、处理状态、结果和预览。
- 按事件游标读取任务更新，避免每次拉取所有历史数据。

状态变更通过具体命令校验，不允许客户端随意 PATCH 为 `completed`。耗时操作快速返回任务或消息标识，再读取执行结果。初期可使用可见页面短间隔增量轮询，隐藏页面降低频率；这只是显示机制，不是后台执行器。

现有 Node 服务用全局 promise 队列串行处理请求，不能把模型等待或整个多步骤任务继续放在其中。应缩短锁的范围到状态写入和领取任务，并对同一任务进行并发控制。

### 状态与恢复

```text
draft → ready → running → completed
                   ↕
          waiting_input / waiting_confirmation / paused
                   ↓
                 failed → 校验检查点后恢复

可取消状态 → cancelled
```

- 进行中列表只纳入 V4 指定的 ready、running、waiting_input、waiting_confirmation、paused、failed，并将需要用户决策的任务置顶。
- 每一步执行前持久化领取记录，完成后保存输出和检查点。页面关闭不影响正在运行的服务；服务器停止时任务停止，重启后需根据检查点核对恢复，不能承诺服务器关机仍继续。
- 暂停发生在安全边界；不能中断的外部动作需说明“完成当前步骤后暂停”。取消不代表已经发生的外部操作被撤销。
- 用户补充要求先经过解析、版本校验及计划更新，实际纳入后才显示“已纳入”；已经完成的步骤不悄悄改写。
- 已执行成功的步骤不重复执行。超时但可能已成功的外部操作进入“结果待核对”，先核对，不能直接自动重试。
- 所有执行前重新检查授权、计划版本和确认范围；参数、证据或目标变化使旧确认失效。
- 进度来自真实步骤；ETA 无可靠依据时显示“正在估算/暂无法估算”，不用定时器制造进度。

Cloudflare 路径还需选择并配置能持久化执行状态的后台调度/执行能力。现有 Worker 请求处理及 D1/R2 存储本身不等于后台任务平台。未完成这一基础设施接入前，不把云端“离开页面继续执行”列为已验收。

## 8. 模型、证据和安全边界

### 模型与路由

- 增加统一模型适配层，服务端管理凭据，支持超时、错误和取消；具体供应商、模型、费用和数据发送范围需要实施前确认。
- 自动模式按是否需要外部工具、交付物或持续执行来建议升级；用户可覆盖模式。仅问答模式不能暗中调用外部工具。
- Chatbot 可以读取用户允许的内部上下文，但发送至模型的数据应受同样的权限与证据范围限制。
- 未配置模型时明确提示“尚未配置”，不能用固定模板假装已经完成自由问答。

### 证据

- 复用现有记录版本和来源信息，区分“今日证据”与“历史记忆”；不为好看生成虚构来源数量。
- 事项入口默认保持单事项上下文隔离；全局提问需要独立定义检索范围，不放松现有事项隔离规则来实现跨事项问答。
- 当前上下文有效性检查倾向于校验事项的完整记录集合，需改为能验证“本次选中的来源及版本”，否则排除证据会被误判为上下文不完整。
- 排除后重算尚未执行的计划与答案；原有结果保留原始证据快照并标注已过时。已发生的外部动作不能因排除证据而自动撤销。

### 确认和授权

- 工具“已接入”、用户“已授权”和单次动作“已确认”是三个不同状态。
- 外部发送、提交、预订等动作必须展示精确目标和参数，并获得当次有效确认。
- 付款与验证码由用户手动处理，不纳入自动执行。
- 授权撤销后阻止后续调用，明确说明受影响任务；不得把已经外发的数据描述成已被撤回。
- 模型输出、上传文件与引用记录均视为内容，不允许其中的指令越过系统授权和执行确认。

## 9. 附件、语音和交付物

- 附件需要新增真实上传和保存流程。现有 JSON 请求体上限约 256KiB，不能用它直接塞入录音或大文件；需单独的上传协议、容量限制、类型校验、解析状态和访问控制。
- 图片、文件和录音先保存并获得引用，再提交消息；上传失败、解析失败与发送失败分别呈现。
- 语音包含麦克风许可、开始/停止、实时转写、取消/发送。转写来源未确定前，该功能只能作为待接入能力，不能将录音成功当成转写成功。
- 首批真实交付沿用 DOCX。原型中的 PDF/Word+PDF 需另加导出器后才能启用；不使用后缀改名假装格式转换。
- 轻预览优先根据结构化准备稿渲染，明确这是内容预览，不承诺与 Word 分页完全相同。
- 系统分享检测浏览器能力，无支持时提供下载或复制可分享内容。受保护的本地结果不能随意转换成公开链接。
- 浏览器下载、保存到服务端、同步到电脑是不同交付状态。没有桌面端或云盘连接时，不显示“已同步到某电脑”。
- 本地和 Worker 的安全响应头同步调整，仅增加实际需要的媒体/预览来源，不整体关闭 CSP。

## 10. 实施批次

### 第一批：基础契约与页面骨架

确定模式、实体、状态机、权限和版本约束；拆出助手模块；完成首页、会话、计划、列表、详情、证据和状态组件。设计验收可以使用独立测试夹具，但测试数据不接入正式任务列表、不伪装真实执行。

交付：可核对 V4 布局和交互路径的页面，以及双端可编译的工程结构。

### 第二批：本地数据与真实任务闭环

实现 AssistantStore、会话和消息持久化、任务命令、检查点、追问和确认；接入现有准备稿、DOCX 和导出核对能力。完成离开页面、刷新、暂停、失败恢复和历史结果访问。

交付：基于已支持文稿能力的真实任务闭环，不依赖虚假进度或虚假工具。

### 第三批：模型、语音和附件

在模型及转写方案确认后接入真实问答、路由判断、升级和要求变更；增加附件上传与受控解析、语音输入。配置缺失、网络失败和用户拒绝权限均有完整路径。

交付：V4 双模式主链路；此批完成前，不宣称通用 Chatbot 已完成。

### 第四批：外部工具与云端适配

按明确选定的日历/云盘/桌面等工具分别接入授权、确认、回执和幂等核对；实现 D1/R2 助手数据适配和选定的云端后台执行器。

交付：逐项验证过的工具能力与云端运行能力。工具账号、OAuth、桌面程序、云资源和部署授权是外部依赖，不属于“画好页面即可完成”。

### 第五批：端到端验收

覆盖 V4 的验收路径，补齐自动化测试并做移动端视觉检查；回归今日、记忆、我的及旧准备稿导出。根据实际可用工具分别记录“通过”“未接入”“不适用”，不以静态页面代替功能验收。

## 11. 验收清单

- [ ] 进入助手 5 秒内可辨识当前模式；首页建议至计划的路径不超过文档要求的两次操作。
- [ ] 问答与任务切换保留消息、附件和证据；升级不会创建重复会话。
- [ ] 计划可编辑，任务开始后持续显示当前步骤、可信进度和 ETA 或不可估算说明。
- [ ] 离开页面、切换模块、刷新后任务仍可恢复查看；本地服务重启按检查点核对恢复。
- [ ] 追问一次一题；等待回答和确认的任务在列表优先展示。
- [ ] 外部动作有具体内容确认；变更参数后旧确认不可复用；撤销授权立即阻止后续动作。
- [ ] 失败恢复不重复已完成步骤；重复点击、网络重试、重复事件不会造成重复导出或外部写入。
- [ ] 排除证据会改变后续判断；越权来源不可访问；旧结果保留来源版本。
- [ ] 完成结果可预览、打开或下载、分享或明确降级，并可继续修改。
- [ ] 未接入模型、语音、PDF、日历或电脑同步时，不呈现虚假成功。
- [ ] 离线保存未发送输入；恢复连接后可重试且不会重复发送。
- [ ] 所有新实体、文件与事件按用户隔离；附件和模型内容不能绕过确认机制。
- [ ] 覆盖约 375/390/430px 手机宽度、桌面容器、软键盘、字号放大和键盘操作。
- [ ] 补充状态机、证据筛选、计划版本、授权、执行恢复、存储读写与迁移、API 合约及端到端测试。当前仓库未见配套测试文件，不能把测试命令零用例通过当作验证完成。
- [ ] 接入 V4 列出的行为事件；统计字段避免记录完整聊天、文件正文、授权凭据等敏感内容。

## 12. 建议采用的初始边界

先在现有 `assistant` 分支完成本地真实闭环，保留现有框架和数据；首批交付物采用 DOCX，云端适配不与本地启动绑死。界面按完整 V4 设计，未接入能力明确标记，不以演示填充业务结果。

开始模型和外部工具开发前，需要确认：模型服务与数据发送范围、语音转写服务、必须接入的首批工具、是否必须同时支持 PDF，以及本次是否包含云端发布。这些选择影响接入工作量，不影响先进行第一、二批的基础开发。
